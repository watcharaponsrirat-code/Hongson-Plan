# Internal implementation contract

Local Node.js (node:sqlite, no packages) + browser ES modules. All Thai user-facing UI. Fresh installations create their first administrator through setup; existing data is preserved. The standalone Pages build uses browser-local profiles without password authentication. API JSON uses amounts in integer satang. UI converts baht. No remote integrations enabled.

## Server transport
GET /api/setup -> {required:boolean}; public, true only when the users table is empty.
POST /api/setup {username,name,password} -> {user,csrf} plus an HttpOnly session cookie. Username is trimmed/lowercased, matches [a-z0-9_.-]{3,40}; name is nonempty, max 150 characters; password is a string of 12–200 characters. Creates one active admin with a system.setup audit entry. Setup has no preexisting session/CSRF token but still rejects foreign Origin/cross-site POST. Rechecks emptiness inside the write transaction; concurrent or later attempts return 409. Invalid fields return 400.
GET /api/bootstrap -> {user:{id,name,roles}, users:[{id,username,name,roles}], state, csrf, integrations:{sheets:false,phone:false}}
POST /api/login {username,password} -> user + csrf (httpOnly session cookie)
POST /api/logout
All other mutations POST /api/action {action,...payload}, X-CSRF-Token header. Result {state, result}. GET bootstrap provides only authorized objects (teacher own; operational roles all). Server enforces mutation authorization. Unauthenticated protected API requests return 401 with setupRequired:boolean so the UI can distinguish initial setup from login. GET /api/health public. GET /api/export?type=... authenticated CSV export. POST /api/upload {name,type,data(base64),projectId} -> {id,name}; GET /api/files/:id authenticated. Max 5MB safe download attachment. JSON max 8MB. GET /downloads/material-prices-2569.xlsx is a public static workbook download.

CSV exports apply `fiscalYear`, `academicYear`, `term`, `group`, `projectId`, and `source` filters to the latest approved project snapshot, within the caller's visible state. A source filter excludes projects without that source; budget/quarter rows and approved amounts are limited to the selected source. Summary exports include only current `submitted`, `accepted`, or `returned` summaries, matching the report screen; drafts and projects without a submitted summary are excluded. Their paid amount is `summary.actualPaid` captured on submission, including a zero snapshot, rather than current payments. This summary amount is the whole project's submission snapshot even when a source filter selects projects. The standalone Pages demo uses the same CSV projection rules.

## State
{projects:[],versions:[],requests:[],commitments:[],payments:[],summaries:[],audit:[],outbox:[],allocations:[],references:[],settings:{projectDeadline:'',summaryDeadline:'',reminderDays:7},notifications:[]}
Every mutable entity id UUID; version optimistic integer required on edits/transitions (new records version=1). project has approvedVersionId; versions are immutable snapshots. Server-generated audit entries. All timestamps UTC ISO. user roles: teacher, planner, plan_head, director, procurement, finance, admin. openDatabase and createApplication default to seed=false: no shared-password accounts or fabricated reference rows. Explicit seed=true remains available to isolated test fixtures. Existing databases retain their users, records, histories and password hashes without reseeding or resetting. Administrator manages users/reference records/settings, not a super-approver; assign teacher or operational roles separately.

Server `user.save` requires admin and uses normalized username/name limits from setup. Creating a user or changing a password requires a string of 8–200 characters; an omitted/empty password on edit retains the existing hash. Edits require the current version and revoke existing sessions for that user. The last enabled administrator cannot be disabled or lose the admin role.

## Frontend files

### Material prices and project suggestions (2026-11-26)

`public/material-catalog.json` contains schemaVersion, version, currency:'THB', priceUnit:'satang', sources, items, unpricedItems and issues. Current source is `ราคาเครื่องเขียน 2569 (2).xlsx`, with 790 numeric price choices and 21 ambiguous/unpriced choices retained as raw text rather than zero or a guessed amount. Genuine and equivalent ink columns are separate items. `scripts/import-material-prices.mjs` builds the catalog reproducibly from the workbook, resolves supported direct cell-reference formulas and rejects unsupported/mismatched source structure. Catalog item IDs include source hash, sheet, row and column.

Server startup inserts missing catalog price rows into state.references without replacing existing edited rows. Bootstrap supplies state.materialCatalog metadata (excluding items); numeric selectable rows come from state.references. The Pages build embeds the same catalog. The picker searches words across name/code/spec/brand/unit/category/origin and filters category. Adding a choice copies its current price, unit and details into an editable resource. No Google Sheets fetch occurs.

Resources may include `priceReference:{id,origin,edition,sourceFile,sourceSheet,sourceRow,sourceColumn,sourceHash,unitPrice,unit}` alongside their own editable unitPrice/priceVersion/priceDate. On save the domain resolves this provenance from the referenced price row rather than trusting submitted labels or source metadata. For an existing resource with the same resource ID and reference ID, it preserves the prior provenance snapshot even after catalog edits. A changed/new reference must resolve to an existing price row. The resource's chosen price can differ from the source price; approved project and amendment snapshots preserve both.

The editor supplies year/term/administration-group/quarter selections and datalist suggestions for months, people, units, funding sources and signature fields. Suggestions do not create authoritative reference entries or replace saved values. Spending month allocations remain separate resource data. School heading 3–4 and 6–11 selectors keep their strict ID-based rules below.

### Standalone browser workspace (2026-11-26)

`build-pages.mjs` embeds the existing workflow with `createBrowserDemo({workspace:true,...})`. Persistence remains scoped to the website path in IndexedDB; per-tab selection uses sessionStorage. A fresh workspace has no projects or profiles. Its local `/api/setup` operation creates the first named profile with all workflow roles; subsequent profiles can be created/edited through user.save. These operations are in-process adapter calls, not HTTP authentication. Anyone with access to the browser can select an enabled profile, so workflow roles do not establish identity or server-side authorization.

Browser-local profile usernames match [a-z0-9_.-]{3,64}; names are nonempty and at most 200 characters. Profiles have id, username, name, roles, disabled and optimistic version, with at least one enabled admin retained. No password is collected or stored. Existing demo documents and backup imports retain original profile IDs/ownership, histories and attachments; their fixed demo profiles become editable local profiles. Current backups use format:'hongson-plan-backup', version:1; legacy 'hongson-pages-demo-backup' remains accepted. Import replaces the browser document only after validation and UI confirmation. Neither mode syncs data to SQLite or other devices.

Build output includes index.html plus public/downloads/material-prices-2569.xlsx beside each emitted HTML file. Runtime code/catalogs/styles are inline; the workbook download is a separate asset. Package-pages includes both. Missing download source fails the build before output is written.

### School reference selectors (2026-11-11)

The project editor uses an immediate single-select dropdown for heading 3 and derives heading 4. Headings 6–11 show grouped checkboxes: parent checks reveal children, leaf checks update selections immediately, and unchecking a parent clears its descendants using stored snapshot ancestry as well as the current hierarchy. Each category has one optional text/number filter; filtering cannot create an option or submit the form. Full labels wrap without ellipsis. Expansion and query state are transient; selections use the same API below.

Bootstrap adds `state.schoolReferenceCatalog` read from `public/school-reference-data.json` when present, otherwise `public/school-reference-data.pages.json`, separate from editable `state.references`. Invalid local contents report unavailable rather than silently selecting another catalog. Catalog `{schemaVersion,version,sources:[{file,sha256,pages}],issues,items:[{id,category,code,name,parentId,source:{file,page,locator},strategyId?}]}` contains the complete supplied source lists. Categories: `strategicProject`, `strategy`, `standards`, `obecPolicy`, `onesqa`, `worldClass`, `kpd`, `hongson`. The synthetic example catalog is an explicit test fixture only.

New project/proposed form data sends `referenceSelections:{category:[{id}]}`. The server ignores client reference labels, versions, sources and hierarchy; validates IDs, category, leaf choice and duplicates; and derives `strategy` only from the chosen strategic project's `strategyId`. `strategicProject` is single-select; other alignment categories allow multiple entries. Result rows store `{id,category,code,name,parentId,path:[{id,code,name}],text,fullText,version,dataVersion,source,snapshotAt,strategyId?}`. `referenceDataVersion` and compatibility text fields are stored too. Unchanged server-side snapshots survive central catalog rename/removal, including on project submission, approval, request proposals and printing.

Existing legacy narratives are preserved in `legacyReferences:{category:[{text,resolvedIds:[]}]}`. Client edits cannot delete or forge this history. Explicit `legacyReferenceResolutions:{category:[selectedId,...]}` confirms matching. Changes to selected IDs invalidate earlier matching until reconfirmed. Submission blocks unresolved old narratives. HTTP project/request save rejects newly typed alignment text without selection IDs; unchanged old text may be preserved. A blank legacy payload can upgrade to empty selectors without losing non-reference fields. Direct `validateProject` without a selector schema remains compatible with historical data tooling.

### Requests before project approval (2026-11-11)

`request.save.projectId` is optional/null for a draft. SQLite migrates existing `requests.project_id` to nullable while preserving bodies and history. Unlinked drafts are visible only to their owner, editable with optimistic versions, and can later link to an owned project. An existing link/type stays immutable. Evidence uploads still require a linked project.

All six types may link to draft/submitted/reviewed/approved/returned projects. Creation stores `original` from the approved snapshot when present, otherwise current project data; `baseApprovedVersionId` can be null. Submission requires an owned linked project and the usual reason/type-specific data, but does not require project approval. Preapproval spend/purchase requests need positive amount/source; procurement still checks available approved funds at confirmation. Creation/submission never alters project, versions, outbox, budget, quarters or commitments.

Request review/approval retains existing roles and return flow. An approved amendment with a non-null base version follows existing snapshot, stale-version and budget-obligation checks. An amendment based on a never-approved version records `amendmentApplied:false` and request approval only; it does not create initial project approval or mutate project data. `unable` still never releases commitments. Procurement confirmation and payment retain idempotency and source budgets.
